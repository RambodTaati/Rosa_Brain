# SQL essentials (original)

SQL queries relational databases. Statements: SELECT, INSERT, UPDATE, DELETE, and DDL like CREATE TABLE.
SELECT id, email FROM users WHERE active = TRUE ORDER BY created_at DESC LIMIT 20;
Joins: INNER JOIN matching rows; LEFT JOIN keeps left rows with NULLs on right when missing.
SELECT u.email, o.total FROM users u INNER JOIN orders o ON o.user_id = u.id;
Aggregates: COUNT, SUM, AVG, MIN, MAX with GROUP BY; HAVING filters groups.
INSERT INTO users (email, name) VALUES (?, ?); — use parameter placeholders for your driver.
UPDATE users SET name = ? WHERE id = ?;
DELETE FROM sessions WHERE expires_at < NOW();
NULL means unknown; use IS NULL / IS NOT NULL, not = NULL.
Transactions: BEGIN; ... COMMIT; or ROLLBACK on error. Keep transactions short.
Indexes speed lookups on frequent WHERE/JOIN columns; they cost write time and space.
Primary keys uniquely identify rows; foreign keys enforce relationships.
Normalization reduces duplication; deliberate denormalization can speed reads when measured.
Views store queries; use carefully for security and performance.
EXPLAIN (vendor-specific) helps understand plans — learn your engine (PostgreSQL, SQLite, etc.).
SQLite is great for local/dev; PostgreSQL for concurrent production apps.
Defensive: never concatenate untrusted strings into SQL. Use bound parameters always. Limit result sizes. Prefer least-privilege DB users for the app role.
Migrations: version schema changes; avoid destructive changes without backups.
Practice: write a SELECT that returns each user and their order count including users with zero orders (LEFT JOIN + COUNT).
Practice: update a status with a WHERE that prevents updating already-final rows.
Q: INNER JOIN vs LEFT JOIN? A: INNER keeps matches only; LEFT keeps all left rows and nullable right columns.
Q: How to avoid SQL injection? A: Parameterized queries / bound parameters, never string-built SQL from user input.
