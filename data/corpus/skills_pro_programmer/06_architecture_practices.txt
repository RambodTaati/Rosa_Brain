# Architecture and professional practices
SOLID-ish practical: single responsibility per module; open for extension via interfaces; do not surprise callers; small interfaces; depend on abstractions at boundaries.
Boundaries: UI -> API -> application services -> domain -> persistence; dependencies point inward.
Feature slices: group by feature folder when it speeds change; shared kernel stays thin.
No stubs in production paths: if a feature ships, it works end-to-end or it is behind an explicit flag.
Code review checklist: correctness, security (authZ, validation), performance obvious wins, tests, naming, migrations safety, observability, docs/changelog.
Observability: metrics (latency, errors), logs (structured), traces (optional); alerts on user-visible failure.
ADRs for non-trivial decisions; short and dated.
Avoid distributed monolith accidental complexity; start modular monolith unless scale demands split.
Idempotent consumers for queues; at-least-once delivery assumed.
Config: 12-factor; distinct prod/stage/dev; feature flags documented.
Graceful degradation: if search is down, list still works.
Delete unused code; comment why for non-obvious invariants only.
API contracts owned with consumers; version consciously.
Data ownership: one writer service per table when split.
Security architecture: threat model light notes for sensitive features; trust boundaries drawn.
